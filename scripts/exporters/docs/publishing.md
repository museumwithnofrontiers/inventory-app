# Publishing a data package

How every exporter's `--publish` turns an export into a released version of a
`@museumwnf/<name>-data` package on npmjs. Each exporter's `NPM_PUBLISH.md`
gives its own command and what is specific to it; this guide covers what they
share.

Every package's source lives in
[museumwithnofrontiers/data-packages](https://github.com/museumwithnofrontiers/data-packages),
one folder per package under `packages/`. An exporter writes its export
there. That repository's release workflow publishes it once the pull request
carrying it is merged (museumwithnofrontiers/inventory-app#2433). Nobody
publishes by hand and nothing here needs an npm login.

## The cycle

Clone data-packages next to inventory-app once. Then for each release:

```bash
git -C ../data-packages switch main
git -C ../data-packages pull
git -C ../data-packages switch -c feature/<what-changed>
docker compose --profile jobs run --rm exporter <exporter> [<exporter options>] --force --publish --base-url https://inventory.metanull.eu
```

That run:

1. Exports the dataset to `scripts/exporters/<exporter>/output/<slug>/`
2. Compares it with `packages/<name>-data/` in the data-packages checkout.
   When only `generatedAt` differs, it writes nothing and says so: there is
   nothing to publish.
3. Otherwise it replaces the folder's content with the export, with the next
   patch version (see below) in its `package.json`

Then commit `packages/` on that branch and open a pull request in
data-packages. Its CI checks the layout and the version of every package the
pull request changes. Merging it publishes each changed package, with
provenance. Then propagate the new versions to the sites, as
[`docs/deployment/release-and-propagation.md`](../../../docs/deployment/release-and-propagation.md)
describes.

`exporter all --force --publish` stages every instance in one run. It ends
with the `propagate.mjs` line for the packages that got a new version, to
paste once the pull request is merged and released.

The `exporter` service mounts the checkout at `/var/www/data-packages`.
`DATA_PACKAGES_PATH` in the environment overrides the default
`../data-packages`. Outside Docker, pass `--data-packages <path>` or set
`DATA_PACKAGES_DIR`.

`--publish` refuses to start without an absolute https `--base-url`: on
2026-10-19 a publish without one shipped relative image URLs to every
website at once.

### Staging schema must be current

The `exporter` service reads `staging-mysql`, not the legacy DB or the app's
own dev database — and `stage` only migrates on a full rebuild. After
pulling a change that adds a migration, run the migration against staging
before exporting:

```bash
docker compose --profile jobs run --rm staging-migrate
```

(non-destructive — `php artisan migrate --force` from the mounted repo). A
full `stage` re-run also covers it. Skipping this can fail the export with
an `Unknown column` error for a field the new migration added. It also
leaves that column **NULL**: columns populated by the importer (e.g. the
project URL map from #1753) only get real values on the next full `stage`,
so a package exported right after a bare migration carries nulls for those
fields until then.

## Version management

The next version is one patch above the later of two: the version the
package's `package.json` holds in data-packages, and the latest version on
the registry. The registry is ahead when the checkout was not pulled; the
checkout is ahead while a merged pull request waits for its release run.
`--package-version <semver>` sets an explicit version instead.

data-packages' CI refuses a changed package whose version is not above the
one on main, or is already published.

## Package structure

```
packages/<name>-data/      (in data-packages)
├── package.json          ← generated by every staging run
├── README.md             ← generated consumer usage guide
├── LICENSE.md            ← copy of docs/LICENSE.md.template (the MWNF legal notice)
├── manifest.json         ← without generatedAt
├── items.json, collections.json, …   (see the exporter's README.md)
└── translations/
    └── <entity>.<lang>.json
```

data-packages commits the JSON pretty-printed, so that a new version is a
line diff. Its release workflow compacts every file again and sets the
manifest's `generatedAt` to the time of the last commit that changed the
folder, so the published package keeps the layout the exporters write.

The `.json.gz` companions an export writes stay in `output/` and are never
staged or published. The `files` allow-list in `package.json` restricts the
publish to `*.json`, `translations/*.json` and `README.md`; npm includes
`LICENSE.md` in the tarball automatically.

## Package metadata

The generated `package.json` carries:

- **name** — the exporter's package name, or the instance file's
  `package_name`
- **version** — see above
- **description** — names the exported project keys or site
- **exports** — `manifest.json` as the entry point, plus every top-level
  `*.json` and `translations/*`
- **repository** — always data-packages, with `directory:
  packages/<name>-data`: npm provenance refuses a package whose repository
  is not the one the release workflow runs in
- **author / license** — from `PACKAGE_AUTHOR` and `PACKAGE_LICENSE` in the
  exporter's `.env`
- **license default** — `SEE LICENSE IN LICENSE.md`, not `UNLICENSED`: the MWNF
  legal notice permits non-commercial/educational use, which `UNLICENSED`
  (all rights reserved) would contradict. `PACKAGE_LICENSE` still overrides it.

## Trusted publishing

The release workflow publishes through npm trusted publishing: npmjs trusts
data-packages' `release.yml` for each package, and the workflow holds no
token. That trust is set once per package, with `npm trust github` (see
data-packages' README).

Trusted publishing cannot create a package. A new package (a new instance
file, say) has its first version published by hand, from a staged folder,
and its trust set, before data-packages' CI accepts it. data-packages'
README says how.

## Troubleshooting

**`--publish` exits immediately with "is not a checkout of
museumwithnofrontiers/data-packages"** — clone it next to inventory-app (or
set `DATA_PACKAGES_PATH`) and retry; the export never ran.

**"unchanged from data-packages: nothing to publish"** — the export matches
what the folder holds. Pull data-packages' main first if a release may have
landed since.

**data-packages CI says the version is already published or not above
main** — another release landed since the export. Pull main into the
branch and rerun the export: it picks the next free version.

**data-packages CI says the package "has never been published"** — a new
package: see Trusted publishing above.
