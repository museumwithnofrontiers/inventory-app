# NPM Package Publishing Guide

How `--publish` turns an export into a released version of
`@museumwnf/islamicart-data` on npmjs. What the package *contains*
is documented in [`README.md`](README.md#what-it-exports); this guide covers
the publishing mechanics only.

The package's source lives in
[museumwithnofrontiers/data-packages](https://github.com/museumwithnofrontiers/data-packages),
in `packages/islamicart-data/`. The exporter writes the export there; that
repository's release workflow publishes it once the pull request carrying it
is merged (museumwithnofrontiers/inventory-app#2433). Nobody publishes by
hand and nothing here needs an npm login.

## Quick start

Clone data-packages next to inventory-app once, then for each release:

```bash
git -C ../data-packages switch main
git -C ../data-packages pull
git -C ../data-packages switch -c feature/islamicart-data-<what-changed>
docker compose --profile jobs run --rm exporter islamicart --force --publish --base-url https://inventory.metanull.eu
```

That run:

1. Exports the dataset to `output/islamicart/`
2. Compares it with `packages/islamicart-data/` in the data-packages
   checkout. When only `generatedAt` differs, it writes nothing and says so:
   there is nothing to publish.
3. Otherwise it replaces the folder's content with the export, with the
   next patch version (see below) in its `package.json`

Then commit the folder on that branch and open a pull request in
data-packages. Its CI checks the layout and the version; merging it
publishes the version, with provenance.

The `exporter` service mounts the checkout at `/var/www/data-packages`
(`DATA_PACKAGES_PATH` in the environment overrides the default
`../data-packages`). Outside Docker, pass `--data-packages <path>` or set
`DATA_PACKAGES_DIR`.

### Staging schema must be current

The `exporter` service reads `staging-mysql`, not the legacy DB or the app's
own dev database — and `stage` only migrates on a full rebuild. After
pulling a change that adds a migration, run the migration against staging
before exporting:

```bash
docker compose --profile jobs run --rm staging-migrate
```

(non-destructive — `php artisan migrate --force` from the mounted repo). A
full `stage` re-run also covers it. Skipping this can fail the export with
an `Unknown column` error for a field the new migration added. It also
leaves that column **NULL**: columns populated by the importer (e.g. the
project URL map from #1753) only get real values on the next full `stage`,
so a package exported right after a bare migration carries nulls for those
fields until then.

## Version management

The next version is one patch above the later of two: the version
`packages/islamicart-data/package.json` holds, and the latest version on the
registry. The registry is ahead when the checkout was not pulled; the checkout
is ahead while a merged pull request waits for its release run.
`--package-version <semver>` sets an explicit version instead.

data-packages' CI refuses a changed package whose version is not above the
one on main, or is already published.

## Package structure

```
packages/islamicart-data/      (in data-packages)
├── package.json          ← generated by every staging run
├── README.md             ← generated consumer usage guide
├── LICENSE.md            ← copy of docs/LICENSE.md.template (the MWNF legal notice)
├── manifest.json         ← without generatedAt
├── items.json, collections.json, partners.json, …   (see README.md)
└── translations/
    └── <entity>.<lang>.json
```

data-packages commits the JSON pretty-printed, so that a new version is a
line diff. Its release workflow compacts every file again and sets the
manifest's `generatedAt` to the time of the last commit that changed the
folder, so the published package keeps the layout the exporter writes.

The `.json.gz` companions the export writes stay in `output/` and are never
staged or published. The `files` allow-list in `package.json` restricts the
publish to `*.json`, `translations/*.json` and `README.md`; npm includes
`LICENSE.md` in the tarball automatically.

## Package metadata

The generated `package.json` carries:

- **name** — `@museumwnf/islamicart-data` (hardcoded in the exporter CLI)
- **version** — see above
- **description** — names the exported project keys
- **exports** — `manifest.json` as the entry point, plus every top-level
  `*.json` and `translations/*`
- **repository** — always data-packages, with `directory:
  packages/islamicart-data`: npm provenance refuses a package whose
  repository is not the one the release workflow runs in
- **author / license** — from `PACKAGE_AUTHOR` and `PACKAGE_LICENSE` in
  `.env`
- **license default** — `SEE LICENSE IN LICENSE.md`, not `UNLICENSED`: the MWNF
  legal notice permits non-commercial/educational use, which `UNLICENSED`
  (all rights reserved) would contradict. `PACKAGE_LICENSE` still overrides it.

## Publishing

The release workflow publishes through npm trusted publishing: npmjs trusts
`museumwithnofrontiers/data-packages`'s `release.yml` for this package, and
the workflow holds no token. That trust is set once per package, with
`npm trust github` (see data-packages' README). Trusted publishing cannot
create a package, so a brand-new package's first version is published by
hand before it moves to data-packages.

## Consumer usage

```bash
npm install @museumwnf/islamicart-data
```

```javascript
import manifest from '@museumwnf/islamicart-data/manifest.json' assert { type: 'json' }
import items from '@museumwnf/islamicart-data/items.json' assert { type: 'json' }

// Lazy-load translations for a language
const { default: t } = await import(`@museumwnf/islamicart-data/translations/items.${lang}.json`)
```

All data files sit at the package root (there is no `data/` directory);
per-language translation files live under `translations/`.

## Troubleshooting

**`--publish` exits immediately with "is not a checkout of
museumwithnofrontiers/data-packages"** — clone it next to inventory-app (or
set `DATA_PACKAGES_PATH`) and retry; the export never ran.

**"unchanged from data-packages: nothing to publish"** — the export matches
what the folder holds. Pull data-packages' main first if a release may have
landed since.

**data-packages CI says the version is already published or not above
main** — another release landed since the export. Pull main into the
branch and rerun the export: it picks the next free version.
